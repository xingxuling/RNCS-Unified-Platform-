# 29｜远程 Provider 与执行沙盒边界反演 v0.8

## 异常

传统 API、云函数、插件、本地脚本和设备驱动被当成不同技术，但它们都在接受输入并产生外部状态变化。

## 矛盾

v0.7 已经知道“谁能做、谁允许做”，但如果执行层没有超时、取消、资源上限、供应链签名和幂等，授权仍可能在落地时失真。

## 本质

Provider 的共同结构不是网址或进程，而是：

```text
可验证身份
+ 能力描述
+ 运输方式
+ 权威范围
+ 资源预算
+ 失败语义
+ 执行证据
+ 现实提交
```

## v0.8 结构

- `capability_binding` 决定候选能力与权威；
- `execution_fabric` 决定允许怎样执行；
- Provider descriptor 签名保证执行对象没有被静默替换；
- idempotency key 防止网络重试重复改变现实；
- circuit breaker 防止持续调用失效 Provider；
- RFE commit 把成功回执从“日志”升级为权威历史。

## 反证

如果统一执行层让简单本地调用明显更慢、更难调试，或无法在真实宿主上实施有效隔离，则应保留分层：低风险纯函数走轻量路径，高风险外部变化才进入完整执行织构。

# HNAF / HNAC v0.6 自适应界面边界反演

## 1. 异常

所谓“跨平台应用”通常只是把同一套页面缩放到不同屏幕：桌面页面塞进手机，手机页面搬进平板，XR 再单独重做一次。应用格式看似中立，界面仍然被 HTML、Android View、UIKit 或某个引擎场景锁定。

## 2. 矛盾

用户目标和应用行为可以保持不变，但输入方式、屏幕尺寸、无障碍要求与空间能力会变化。若把固定页面当成应用本体，每增加一种宿主，就要复制一套 UI、事件处理和状态绑定。

## 3. 本质

界面由三层组成：

```text
语义：这是什么、为什么存在、与什么状态有关
意图：用户想触发什么动作、风险和确认要求是什么
投影：当前宿主用什么控件、布局和感知方式表达
```

真正应随胶囊携带的是前两层；第三层属于宿主。

## 4. v0.6 结构

AIP v0.6 使用有向无环语义图：

- `action`：可执行意图；
- `information`：状态或解释；
- `navigation`：区域与路径；
- `document`：长内容与结构；
- `media`：图像、音频、视频或说明；
- `spatial`：空间锚点及非空间回退；
- `group`：语义分组。

宿主资源上下文决定投影：

| 宿主 | 主要投影 |
|---|---|
| desktop | 多窗格、侧栏、紧凑控件 |
| tablet | 自适应网格、导航轨道、触控目标 |
| phone | 单列、底部导航、全宽动作 |
| accessibility | 线性阅读、地标、命令语义 |
| spatial | 世界锚点、门户、空间控制 |

投影结果被规范化并计算 `semantic_snapshot`，因此 Python、Node 与浏览器宿主可以比较“表达语义是否相同”，而不是比较像素是否相同。

## 5. 输入反演

传统界面把 `click`、`tap`、快捷键、语音命令分别绑定业务函数。v0.6 先把它们解析为统一意图：

```text
pointer.activate ┐
touch.tap        ├─→ app.run
keyboard.Enter   ┤
voice.运行应用    ┤
neural.confirm   ┘
```

`neural` 只表示未来设备可以提交结构化候选事件；它不等于已经实现脑电解码，也不允许绕过权限和确认。

## 6. 现实价值

- 一个胶囊可由不同设备形成合适界面；
- 应用身份、状态和意图不随 UI 技术栈复制；
- 无障碍不再是页面完成后的补丁，而是正式投影；
- XR 与未来神经宿主可以沿同一意图边界接入；
- 可以验证跨宿主语义，而不要求像素完全一致。

## 7. 反证条件

v0.6 路线在以下情况下应被否定或收缩：

1. 简单应用的语义图长期比直接写页面更复杂；
2. 宿主投影无法保留关键业务含义；
3. 自适应规则导致用户行为不可预测；
4. 语义快照只能证明 JSON 相同，不能证明实际可用性；
5. 原生平台能力必须大量逃逸到私有扩展，导致协议名存实亡。

## 8. 锚点

> HNAC v0.6 不再追求“同一页面到处运行”，而是让同一个应用在不同宿主中保持身份、状态、能力与意图不变，同时允许表现形式真正适应设备和主体。

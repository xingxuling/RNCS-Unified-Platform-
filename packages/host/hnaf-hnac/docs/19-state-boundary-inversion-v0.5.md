# 状态边界反演：从宿主文件到可携带现实连续性

## 1. 旧命名隐含的错误边界

“应用状态”通常被实现成数据库、偏好文件、缓存目录、Token 文件和内存变量。名称看似统一，现实边界却被宿主位置决定：换设备、换浏览器、换安装方式后，应用本体与状态被割裂。

## 2. 反演

```text
状态不是“宿主保存了什么”
状态是“哪些事实必须以何种边界持续存在”
```

由此，状态最小问题不再是文件格式，而是：

- 是否应跨设备；
- 是否能明文跨边界；
- 是否可丢弃并重建；
- 是否只属于当前会话；
- 如何迁移、证明、冲突与恢复。

## 3. 五分区不是五个目录

目录只是参考宿主实现。真正合同是：

| 分区 | 连续性 | 跨宿主边界 |
|---|---|---|
| portable | 持久 | 可验证导出与同步 |
| device_private | 持久 | 不可导出 |
| secret | 持久 | 仅认证加密包 |
| cache | 可重建 | 可选导出 |
| ephemeral | 会话 | 不落盘、不导出 |

## 4. 双根模型

- `state_root`：只由应用、Schema 与语义状态计算；同一状态跨宿主同根。
- `snapshot_root`：加入 Replica、Generation、父快照和标签；表达连续性历史。

这样同时避免两种混乱：

1. 同一状态因时间戳、设备名不同而无法比较；
2. 同一内容在不同历史位置被错误视为同一事件。

## 5. 权威边界

v0.5 仍不直接宣称“网络同步完成”。它先冻结可被上层 Gateway、RFE 与 HNAF Pocket 调用的确定性边界：

```text
本地状态
→ 状态根
→ 可验证导出包
→ 迁移
→ 冲突记录
→ 显式协调策略
→ 新快照与 Generation
```

网络、云端或设备桥只负责运输，不得重新定义状态语义。

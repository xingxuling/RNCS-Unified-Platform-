# 构建系统命名边界反演报告 v0.1

## 旧名称：Build / Export

传统引擎通常把构建理解为：把资源复制、压缩，再调用平台编译器生成程序。

这个名称默认了四个边界：

1. 构建只发生在项目完成之后；
2. 构建产物由平台文件格式定义；
3. 开发状态和发布状态是两套相互割裂的世界；
4. “编译成功”就等于“项目现实没有发生错误”。

## 异常

一个项目在编辑器里运行正常，导出后仍可能出现：

- 资产路径丢失；
- 哈希和实际文件不一致；
- 开发目录中存在但发布包缺失的依赖；
- 不同平台偷偷采用了不同逻辑；
- 构建结果无法证明来自哪个项目状态；
- 无法判断产物是否被修改。

本版本实际发现了霜璃资产记录哈希与随包文件不一致，并拒绝发布，随后生成资产对账记录并重新密封项目根。

## 反演

> 构建不是“把项目变成程序”，而是“把同一个权威现实编译为不同宿主可以执行、验证和追溯的发布投影”。

新原语：

```text
Project Reality
+ Target Capability
+ Asset Bake
+ Runtime Selection
+ Platform Adaptation
+ Integrity
+ Evidence
```

## 新名称

**Reality Build Fabric｜现实构建织构**

它维持的不是一个临时输出目录，而是：

- 项目根；
- 语义构建根；
- 构建图；
- 资产内容地址；
- 目标根；
- 文件哈希；
- 构建收据；
- 平台边界声明。

## 生活例子

传统构建像搬家时把房间里的东西全部塞进纸箱，只要货车开走就算成功。

现实构建织构更像国际货运：

- 先核对每件物品是否属于这批货；
- 每件货物有编号和重量；
- 不同国家采用不同包装；
- 装箱单记录依赖关系；
- 收货方可以核对是否少件或被替换；
- 同一件货换了运输方式，身份仍不改变。

## 反证条件

该反演只有在以下条件成立时才有效：

- 多目标来自同一项目现实；
- 资产可复现且可校验；
- 构建路径变化不改变目标内容根；
- 发布后仍运行真实行为程序；
- 缺失依赖或哈希冲突会阻止发布；
- 平台能力不足时明确降级，而不是伪造完成。
